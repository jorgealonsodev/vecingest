# M1 Security Gate — Isolation

PRD_go.md section 10.1, "M1 — Aislamiento": seven verifiable checklist items.
Per PRD section 10: "La puerta se verifica con evidencia (resultado de CI,
informe, captura, entrada en el runbook), no con una afirmación." — the
gate is verified with evidence, never a bare assertion.

Split into two checkpoints so a green CI run is never mistaken for a
closed milestone (`openspec/changes/m1-communities/tasks.md`, Phase 10;
`proposal.md` risk row "M1 gate cannot fully close without DNS/SMTP"):

- **Checkpoint A** — closeable entirely from this repository (code, tests,
  CI runs, documents). No deployed server or DNS is required. **OPEN as of
  2026-10-06, one blocking finding** (next section): every test cited
  below passes on this tree, but CI does not execute the database-backed
  ones, so PRD item 1's "Se ejecuta en cada PR" is not met.
- **Checkpoint B** — requires a deployed server (item 4's manual proof) or
  control of the sending domain's DNS (item 5). **OPEN as of 2026-10-06,
  no evidence collected yet.** It also carries this gate's one scoped
  exception: Turnstile coverage for company signup and contact forms.

Each row cites the spec requirement that carries the acceptance scenarios,
rather than restating the checklist, so the two cannot drift. Where no
spec carries an item (rows 2 and 5) the row cites the design or proposal
text that does. The seven items are the security gate only: PRD section 10
makes the milestone's functional criterion ("Un admin crea una comunidad e
invita a un vecino que entra en su portal") a second, mandatory condition,
and this document does not evidence it.

## Blocking finding — CI does not run the database-backed tests

PRD 10.1 M1 item 1 requires the permission matrix to run "en cada PR", and
`openspec/config.yaml:133` (`permission_matrix.requirement`) restates it as
"on every PR". It does not. `TestPermissionMatrix_ForeignResourceDenied` —
the cross-tenant half, the part that actually proves isolation — is never
executed by CI, and neither are the HTTP-level tests behind rows 3, 6 and 7
or the automated half of row 4. **Every test cited in this document passes
locally on this tree; CI does not execute the database-backed ones.**

Evidence, read from the repository:

1. `newTestServer`, the helper every database-backed `internal/http/api`
   test starts from, skips under `-short`
   (`api/internal/http/api/api_integration_test.go:68`:
   `if testing.Short() { t.Skip(...) }`).
2. CI's `go` job runs `go test -race -short -count=1 ./...` with the Docker
   daemon stopped (`.github/workflows/ci.yml:128-138`), so every
   `newTestServer` test skips there.
3. The `coverage` job covers only `./internal/domain/...`
   (`.github/workflows/ci.yml:175`); `internal/http/api` is not in it.
4. The `e2e` job runs `make test-e2e`, which is `go test -race -count=1
   ./test/...` (`Makefile:37`); `internal/http/api` is not in it either.
   The one M1 test under `./test/...`, `TestM1TenantSchema`, is
   schema-level (`UpDownUpIdempotent`, `InvitationsTable`), not an
   authorization test. `design.md`'s Testing Strategy routes "Tenant
   isolation, invitation expiry, single use" to `make test-e2e`; those
   tests were written in `internal/http/api`, which that target does not
   run.

Where each cited test runs (every CI job that executes tests below is gated
on `changes.backend`: any changed file outside `app/**` and `site/**`):
