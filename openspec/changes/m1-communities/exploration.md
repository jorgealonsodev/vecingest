## Exploration: M1 — Comunidades, viviendas, invitaciones, portales vacíos por rol

### Current State

Repo has commits now (M0 done): 6 tables (`users`, `sessions`, `audit_log`, `password_reset_tokens`, `user_mfa`, `otp_challenges`), 12 auth/health/profile endpoints, no tenant tables at all. `api/cmd/lintscope/` is live and enforces (structurally, over `.sql` files, no DB needed) that every `sqlc` query against a table carrying `community_id`/`office_id`/`company_id` references that column; today it is trivially green because the only table with such a column (`audit_log.community_id`) is an explicit, documented M0 exception. `RequireMembership(scope, roles...)` — the chi middleware PRD_go.md §7.7 names as the *sole* authorization mechanism (\"No se usa RLS de Postgres\") — does not exist in the codebase yet; there is no Postgres RLS anywhere, by design. `app/src/screens/PortalScreen.tsx` (built today) calls the real `GET /v1/me`, renders `{id, email, is_superadmin}`, and shows a hardcoded, honest empty state (\"Todavía no perteneces a ninguna comunidad ni empresa\") plus a disabled invitation-code entry point (`portal-invitation-link`, \"Próximamente\") — both explicitly waiting on M1 tables/endpoints (`docs/pendientes-funcionalidad.md` §1, §2, §4). `api/internal/mail` already has a working `AsyncMailer` (bounded worker pool, SMTP) plus an interim `LogMailer`, and a template pattern (`RenderPasswordReset`, `RenderLoginLockoutAlert`) that an invitation email would reuse; the only gap is that `SMTP_URL` has no real provider credentials in production yet (deployment concern, not a code gap). No MFA HTTP endpoint exists yet — `internal/domain/auth/mfa` (totp, enroll, recovery, throttle) is fully built for M0's superadmin-only 2FA, but there is no `/v1/auth/mfa/enroll|verify|recovery` handler for a non-superadmin user, which M1's \"2FA obligatorio para admin/admin_staff\" gate needs.

### Open Decision 1 — Tenant isolation: what actually proves a query cannot cross communities

PRD_go.md §7.7 has already decided the mechanism (no RLS; app-layer `RequireMembership`); the real open question is **how much of \"cannot cross tenants\" that mechanism actually proves**, since it is two independent layers with a real gap between them:

| Layer | What it checks | What it misses |
|---|---|---|
| `lintscope` (static, exists) | Every `sqlc` query text against a scoped table contains its tenant-column identifier | A query can reference the column and still be wrong (e.g. `WHERE community_id = $1 OR 1=1`); it is a lexical `containsWord` check, not a semantic one. It also says nothing about whether a *handler* ever calls a scoping check at all — it only sees the SQL files. |
| `RequireMembership` middleware (to be built) | Resolves membership for the route's resource and injects it into `context.Context`; PRD says \"un handler sin ella no compila para rutas con ámbito (interfaz obligatoria)\" | This \"does not compile\" guarantee needs an actual Go mechanism to hold — e.g. a required typed parameter on every scoped handler signature — otherwise it is a convention a future PR can silently skip, and lintscope cannot see that because it only reads `.sql` files, not handler wiring. |

Options for closing that middle gap:

1. **Convention + code review only** — rely on the \"handlers receive membership as an explicit argument\" pattern and the security-review PR checklist (PRD §9 point 10). Pros: zero extra machinery, matches the PRD's stated design exactly. Cons: nothing stops a new route from being registered without going through `RequireMembership`; the only backstop is the permission-matrix test catching it *after* the fact, and only if that test enumerates the new route. Effort: Low.
2. **Structural signature enforcement** — every scoped handler's function signature takes a `Membership` struct as a parameter (not from context lookup inside the handler body), and route registration only compiles for handlers implementing a `ScopedHandler` interface requiring that parameter. Pros: matches PRD's literal wording (\"un handler sin ella no compila\"); a missing scope check is a compile error, not a runtime gap. Cons: needs a small amount of registration-time plumbing (an adapter/wrapper type) decided now, before the first scoped handler exists, or it has to be retrofitted across every M1+ handler later. Effort: Low–Medium, one-time.
3. **Registered-route audit test** — a test that walks every route chi has registered and asserts each one under a scoped prefix (`/v1/communities/*`, `/v1/units/*`, `/v1/incidents/*`, …) has `RequireMembership` in its middleware chain, independent of what the handler body does. Pros: catches the \"forgot the middleware entirely\" case that lintscope structurally cannot see (it never reads route registration). Cons: needs route-introspection tooling; a route added to an unscoped prefix by mistake is not caught by this test — it only checks routes that are already under a scoped prefix. Effort: Low, and complements (2) rather than replacing it.

The permission-matrix test PRD §10.1 already requires (\"cada endpoint × cada rol × recurso propio/ajeno; ajeno → 403 o 404 … cobertura del 100 % de rutas\") is the outer backstop regardless of which of the above is chosen, and is mandatory either way — it is the only layer that would ever catch a scoped route pointed at the *wrong* community rather than no community check at all. None of these options is a substitute for it.

### Open Decision 2 — Role and membership model: the minimal M1 shape

PRD_go.md §3 names 7 roles (`superadmin`, `admin`, `admin_staff`, `owner`, `tenant`, `company`, `worker`) plus a `board_role` attribute (`president`/`vice_president`/`secretary`) on `unit_members`, evaluated **per membership, not per user** — a user can hold several memberships (owner in one community, worker at a company). `docs/funcionalidad/README.md` finding 5 records that Stitch's company screens draw finer roles (\"Técnico Campo\", \"Responsable Oficina\") than the schema's two-value `company_members.role` enum — the user has already decided to keep the two-value enum, so this is resolved, not open.

What M1 actually needs, scoped to its own acceptance criterion (\"un admin crea una comunidad e invita a un vecino que entra en su portal\") and its own screens (`docs/funcionalidad/consola-web.md` M1 section, `app-movil-2.md` \"Elegir dónde entrar\"):
- `offices`, `office_members` (role: admin | admin_staff) — needed because `admin`'s access is scoped to communities where `community.office_id` matches one of their `office_members` rows (§3 rule).
- `communities`, `units`, `unit_members` (role: owner | tenant) — the core of the acceptance criterion.
- `GET /v1/me` returning the aggregate of `unit_members` + `office_members` (+ `company_members`, even if empty at M1) is what `PortalScreen`'s context-selector screen and `docs/funcionalidad/app-movil-2.md`'s \"Elegir dónde entrar\" both need — it is a M1-by-elimination screen the inventory explicitly ties to \"portales vacíos por rol\" rather than to any named PRD milestone row.
- `board_role` on `unit_members`: the column exists in PRD's schema draft and could be created now (it costs nothing at the schema level), but *assigning* it is explicitly tied by the funcionalidad inventory to the community-ficha tabs that \"dependen de datos de M5 y M7\" — nothing in M1's acceptance criterion or security gate needs it populated. Decision for propose: create the column now (cheap, matches the PRD table verbatim, avoids a later `ALTER TABLE`) but build no assignment endpoint or UI in M1.
- `company_members`/`companies`: PRD's role table and `office_providers` model them, but no M1 screen or acceptance criterion in the funcionalidad inventory (across all five files) involves company registration or the company portal — see \"Where M1 must stop\" below for the public-registration-endpoint tension this creates with M1's own security gate.

### Open Decision 3 — Invitation flow: states, expiry, abuse, and account creation

PRD's schema for `invitations` (line 540–543) has **no explicit `status` column** — it is derived: `accepted_at IS NULL` = pending, `expires_at < now()` = expired, `failed_attempts >= 10` = locked, and a `DELETE /v1/invitations/:id` (already in §7.4's endpoint list) presumably maps to the same `deleted_at` soft-delete convention every other business table gets (line 492) for \"revoked by admin before acceptance.\" That derivation needs to be confirmed rather than assumed at spec time — the alternative is an explicit `status enum (pending|accepted|expired|revoked|blocked)` matching the pattern every other stateful table in §7.3 uses (`incidents.status`, `meetings.status`, `announcements.status`). Options:

1. **Keep it derived (as drafted)** — Pros: matches PRD's schema exactly, no PRD deviation to justify. Cons: \"locked after 10 failed attempts\" and \"expired\" and \"revoked\" all read as the same thing (`accepted_at IS NULL AND not-pending-anymore`) to a client unless the API computes and returns a derived status string anyway — which means the derivation logic has to live somewhere and be tested regardless.
2. **Add an explicit `status` column, computed transactionally** — Pros: consistent with every other stateful table, one less special case for the API layer to hand-compute on every read. Cons: a PRD schema deviation to record and justify (minor: the PRD's own convention elsewhere argues for it).

Two independent invitation entry points exist in the design and PRD, and they are not yet reconciled with each other: PRD §5 (line 210) describes an email link **or** an 8-character code \"para entregar en papel\" — i.e., a neighbour with no email, or one whose landlord/admin prefers a paper invite, still needs a way in. `docs/funcionalidad/app-movil-1.md` and `app-movil-3.md` independently proposed **two different provisional endpoint shapes** for the same \"preview before accepting\" step (`POST /v1/invitations/validate` + `POST /v1/invitations/{code}/accept` in one file; `GET /v1/invitations/resolve?token=` in another) — neither is in PRD §7.4, which only lists `POST /v1/auth/accept-invitation` (`{token}` or `{short_code}`, no preview). The accept-invitation screen (`app-movil-3.md`, screen `607f8aeb…`) needs to show the community/unit/role *before* the user commits to \"Crear mi cuenta\" — that preview step has no PRD-named endpoint at all and must be decided at propose time (a `GET` preview endpoint accepting either token or short_code seems closest to REST convention and matches PRD's `{token}`/`{short_code}` duality, but the exact route and whether it is a preview-only 200 or the same accept-invitation call gated on a `dry_run` param is unresolved).

Anti-abuse mechanics the M1 security gate names explicitly and unambiguously (§10.1): 14-day expiry, single use, lockout after 10 failed short-code guesses, hashed storage (`token_hash`/`short_code_hash`, both unique) — none of this is ambiguous, it is a checklist to implement against the schema already drafted.

### What \"portales vacíos por rol\" concretely means as a deliverable

Not a new screen — `PortalScreen.tsx` and its desktop analogue already exist and already call `GET /v1/me`. The M1 deliverable is narrowly: (1) `GET /v1/me` starts returning a `memberships` array (community/unit/office/company + role, per `docs/funcionalidad/app-movil-2.md`'s \"Elegir dónde entrar\" backend note), (2) `PortalScreen` renders real selectable rows instead of the hardcoded empty state when that array is non-empty, (3) the invitation-code entry point (`portal-invitation-link`, currently disabled with \"Próximamente\") gets wired to whatever accept/preview endpoints propose settles on. \"Empty by role\" itself (an admin with zero communities, a neighbour who hasn't accepted yet) is already built and already honest — the empty state is not new work, only the populated branch is.

### Where M1 must stop

- **\"Comunidad, resumen\" (`app-movil-1.md`, screen `c7583dc1…`) is explicitly cross-milestone**: the inventory itself flags that its reserve-fund-compliance banner, last-meeting quorum summary, and account balance pull from M5/M7 data, and three of its navigation targets (\"Tareas y despachos\", \"Remesas y liquidaciones\", \"Reclamaciones monitorias\") have **no endpoint or table anywhere in PRD_go.md** — not deferred, unmapped. M1 should build the community-ficha's own basic fields (name, CIF, address, unit/office counts) and stop there; the aggregating dashboard is not an M1 deliverable even though its screen ID sits under the M1 heading.
- **The \"Junta directiva\" ficha tab and `board_role` assignment** are tied by the inventory to M5/M7 data and have no M1 acceptance-criterion driver; create the column, build no UI/endpoint for it.
- **CSV import's formula-injection and path-traversal hardening is explicitly M1** (§10.1 checklist item) and is a real, scoped piece of work — not to be dropped, but scoped to the `POST /v1/communities/:id/units/import` endpoint only, not a general-purpose file-hardening effort.
- **Company registration's Turnstile requirement is a genuine tension worth flagging, not resolving here**: the M1 security gate (§10.1) explicitly requires \"Turnstile en alta de empresa, contacto y recuperación,\" but no M1 functional screen or acceptance criterion in the funcionalidad inventory (across all five files) involves company self-registration — it never appears mapped to any milestone in that inventory. Either M1 must also ship `POST /v1/auth/register-company` + its form (expanding M1's functional scope beyond its own acceptance criterion) purely to satisfy its own gate item, or the gate item is understood as \"install Turnstile on this form whenever it ships\" and is not blocking for M1 sign-off. This needs an explicit propose-time decision, not an inference.
- **Non-superadmin MFA enrollment/verification HTTP endpoints** are real M1 work (the gate requires 2FA mandatory for admin/admin_staff) but reuse M0's already-built `internal/domain/auth/mfa` package — this is endpoint wiring, not new domain logic, and should not be scoped as if the TOTP mechanism itself needs re-deciding.
- **SMTP delivery is a deployment gap, not an M1 code gap**: `api/internal/mail.AsyncMailer` and the SMTP-vs-log-mailer seam already exist from M0; the \"correo autenticado\" gate item (SPF/DKIM/DMARC) is an infra/DNS task with no new Go code, and `SMTP_URL` being an inert production placeholder is a deployment blocker for *proving* the gate with real evidence, not a design question for this exploration.

### Risks
- The `RequireMembership` \"does not compile without it\" guarantee PRD §7.7 asserts is a design intent, not yet a mechanism; if propose does not pick a concrete enforcement shape (Option 2 above, or an equivalent), M1 risks shipping a middleware that is easy to forget on a new route, discoverable only by the permission-matrix test if that test's route enumeration itself stays in sync.
- Three independent, mutually inconsistent draft shapes exist for the invitation-preview/accept endpoint across the funcionalidad inventory files; propose must pick one rather than merging fragments from all three.
- The company-registration/Turnstile gate-vs-scope tension (above) could silently expand M1's functional surface if not decided explicitly.
- `invitations.status` being derived rather than explicit is a minor but real PRD-convention deviation risk that should be confirmed, not assumed, before spec.

### Ready for Proposal
Yes. The domain model, endpoints, and security-gate checklist are already substantially named in PRD_go.md §7.3/§7.4/§10.1; the four decisions above (tenant-isolation enforcement mechanism, board_role/company scope-out, invitation state model + preview endpoint shape, company-registration-vs-gate tension) are the ones sdd-propose needs to resolve explicitly rather than infer.

## Key Learnings
1. `RequireMembership(scope, roles...)` is named as the sole authorization mechanism in PRD_go.md §7.7 but does not exist in code yet — it is pure M1 scope, and its \"handler doesn't compile without it\" guarantee needs a concrete Go mechanism decided at propose time.
2. `lintscope` only reads `.sql` query files lexically; it cannot see whether a handler ever invokes a scoping middleware at all, which is the real residual gap between the two enforcement layers.
3. `GET /v1/me` returning memberships is the single wire that turns `PortalScreen.tsx`'s already-built empty state into the real \"portales vacíos por rol\" deliverable — no new screen is needed.
4. Three funcionalidad-inventory files propose three different, unreconciled shapes for an invitation preview/accept endpoint that has no PRD-named route at all.
